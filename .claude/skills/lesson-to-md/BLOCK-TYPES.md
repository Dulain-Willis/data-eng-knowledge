# Block types

The site builds a lesson from blocks tagged `data-note-block-type="<type>"`, and the converter keys its rules on that tag. Types in `GENERIC_BLOCKS` have real HTML tags and need no rule. The reason behind each rule sits in the comment beside it in `tools/lesson_to_md.py`; this file records what each block's HTML looks like, so a new type can be matched to a solved one.

## Types with a rule

| Type | HTML shape | Handling |
|---|---|---|
| `info_list` | Rows of 1 to 3 sibling spans (label, gray tag, description) with no whitespace between them. The label looks bold through styling, with no `<strong>`, so a search for `**` finds nothing wrong; count spans per `li` instead. | Rows with 2 or more spans become `**label** *tag*` plus the description on its own line. One-span rows stay plain. |
| `rich_info_list` | Like `info_list`, but the label is a real `<strong>`. | None needed. |
| `icon_list` | Rows of a decorative icon plus a sentence in nested divs, with no list tags. | One bullet per row. |
| `static_code` | A table, one row per line, code in the last cell. | Code fence. |
| `big_number` | Stat cards, two divs each: figure, then caption. | Bullets pairing figure and caption. |
| `tip`, `callout`, `fun_fact` | A styled div. `tip` prints its own TIP label. | Blockquote; `tip` bolds its label. |
| `key_takeaways`, `synthesis` | Plain divs with canvas-drawn bullets and no `li`. | `##` heading plus bullets. |
| `pipeline_diagram`, `schema_diagram` | HTML boxes layered with SVG, no text structure. | 2x screenshot. |
| `executable_spark` | A runnable PySpark cell: seed tables on the left, code editor, Run button, and an output table that only appears after Run (drawn by JavaScript). The static HTML holds just the code in a `<pre>`. | `record_cells` clicks Run, waits until the cell text stops changing, and takes one 2x screenshot of the whole cell (`_images/<slug>_cell_<n>.png`, alt `Run output n`); the code follows as a ```` ```python ```` fence (screenshots can cut long lines). Warns on a cell with no output or an error. |
| `executable_python` | A runnable Python cell: macOS-style window, a line-numbered code table, a `>>>` button at the bottom right. The output is already in the static HTML but collapsed; the button reveals it (a toggle, click once). | `record_cells` clicks the `>>>` button (the only button in the cell), waits for the cell to grow, then one 2x screenshot of the whole cell (`_images/<slug>_cell_<n>.png`); code follows as a ```` ```python ```` fence (rebuilt from the table rows). "Predict the output, then reveal" cells are the same control. |
| `executable_sql` | A runnable SQL cell: code window, table-icon button and a result table already in the HTML. The 3 buttons are "Animate this query", "Edit and run this query" and "Show result"; only the exact-name "Show result" is clicked. | `record_cells` clicks "Show result" and takes a 2x screenshot of the whole cell; the code stays as a ```` ```sql ```` fence (`CELL_FENCE`). |
| `table_visualization` | Same player chrome as `sql_animation` (code panel, tables, dots, step counter) but a different block type (5 in `aggregating_beginner`). | Treated as an animation (`ANIMATION_RE` / `ANIMATION_SELECTOR`), recorded as MP4. |
| `sql_parsons` | Drag-the-tiles query assembly puzzle (34 blocks); no answers in the page. | In `SKIPPED_BLOCKS`; the prose that only introduces it is in `tools/drops.json`. |
| `sql_switcher` | A tab strip (buttons with no title) over one caption div, one SQL code table (a row per line, `data-ln` cell, code in the last cell) and a Result table that is in the DOM while collapsed. The saved HTML holds only the first tab's panel and the converter drops `<button>`, so tab names and the other panels exist only on the live page (58 blocks, 152 tabs in Learn SQL). | `sql_switcher_tabs` clicks every tab on the live page and `switcher_panel` parses each state; `switcher_markdown` writes per tab a bold name, the caption, a ```sql fence and `Result:` plus the result as text, no screenshots (Option A of draft PR #24). Without playwright it falls back to the first tab with a warning. |
| `regex_cards` | Stacked cards: pattern, description, example line (`text -> match`). | `record_regex_cards` screenshots the block (`_images/<slug>_regex_<n>.png`); the text of each card follows as a bullet. |
| `spark_animation` | Like the other `*_animation` blocks, but the controls mount lazily once scrolled into view and the static HTML shows "Preparing the animation"; `record_animations` waits for the first button before measuring the player. | MP4, uploaded (see below). |

## Left out on purpose

- **Star ratings (Daily Life, Interviews):** drawn on a canvas by JavaScript, so the page source holds no values.
- **`multiple_choice`:** the rendered options are buttons with no correct-answer marker, but the page's Next.js payload (`self.__next_f.push` script strings) holds `{"type":"multiple_choice","question","options":[{"text","is_correct","explanation"}]}`. `embedded_questions` reads it, matching each block to its JSON by question text, and `multiple_choice_markdown` writes the question, lettered options, then a closed `<details><summary>Solution</summary>` with the correct option, its explanation, and "Why the others are wrong" (one explanation per wrong option).
- **`multiple_choice` JSON quirks:** key order varies (a question with a code snippet has `"code"`, `"language"` before `"type"`), so `embedded_questions` walks back from each `"type":"multiple_choice"` marker to the enclosing object. Inline code in a question renders without its quote marks, so `question_key` drops quotes, backticks and whitespace before matching.
- **`full_width`:** a wrapper around a real table (pa_what_is_a_pipeline_advanced); in `GENERIC_BLOCKS`.
- **`pipeline_animation`:** an animated pipeline widget (retry storms, ingestion flows). Its data is in the page JSON (`nodes`, `edges`, `clock`, `variants`). Not handled yet: it prints "no rule" and falls back to generic conversion, so the animation is lost. Seen in 8 learn/architecture lessons.
- **`schema_story` (data_modeling lessons):** interactive quiz with no answers in the page, so only a dangling question would remain. `SKIPPED_BLOCKS` drops it. Not yet checked for embedded JSON the way `multiple_choice` was.
- **Airflow exercises (tools/airflow):** all left out by the `INCLUDE_AIRFLOW_EXERCISES = False` switch in `tools/lesson_to_md.py`; the converter prints `note: N Airflow exercise(s) left out (INCLUDE_AIRFLOW_EXERCISES is False)` and runs no exercise browser pass. Why: the exercises are badly made. The grid/run-naming forms are buggy (a widget's sentence is sometimes drawn outside its frame, e.g. the 9 UTC / 3 November `signups_daily` one), and Run/Submit need a login. `airflow_animation` blocks are kept (lesson text refers to "the animation below"). To turn exercises back on, set the constant to True: the converter still has the repair-the-DAG conversion (`config.form == "dag_repair"`, Mermaid after-fix graphs, a `What changes` diff); other forms stay left out.
- **dbt and Kafka exercises (tools/dbt, tools/kafka):** also left out, via `SKIPPED_TOOL_EXERCISES = {"dbt", "kafka", "spark"}` in `tools/lesson_to_md.py` (matched on the challenges endpoint's `challenge_type`); the converter prints `note: N dbt|kafka exercise(s) left out`. They are not copies of Airflow's: dbt forms include compile_it, build_outcome, select_the_nodes, two_run_proof, model_it, catch_the_defect, draw_the_lineage, snapshot_timeline; Kafka forms include read_the_tape, assign_the_group, lag_board, crash_point, connector_config, log_cleanup, schema_rollout, delivery_trace, route_the_keys, durability_dial, replica_trace. No conversion code exists for them. The `placed_challenge` stub is dropped and `dbt_animation` / `kafka_animation` blocks are kept as GIFs. Lesson titles still say "N challenges", and a few sentences in the text point at the removed exercises (kafka_the_log_advanced has two "the drill below" paragraphs).
- **Prose that points at a dropped exercise:** a hand-kept list, `tools/drops.json` (`{slug: [text prefix of each block to drop]}`), applied only when a lesson's exercises are left out (`convert(..., drop_exercise_refs=True, drops=...)`). It is a list on purpose: no pattern deletes anything. Entries today: 2 Spark (`spark_execution_model_beginner`, `spark_narrow_wide_shuffle_advanced`), 2 Kafka drill sentences in `kafka_the_log_advanced`, plus 2 dormant ones for learn data modeling (`data_modeling_dimensional` "The story below...", `data_modeling_relationships` "Capstone: design the reactions model") that only take effect if those lessons ever drop their exercises. A stale entry prints a warning. For a new category (Spark, SQL, Python), convert it, scan the result for "below"/"capstone" lines next to an exercise, review the hits by hand and add entries. `strike` in `kafka_replication_intermediate` belongs to a kept animation, so it stays.
- **Spark exercises (learn/spark):** challenge_type `spark`, left out through `SKIPPED_TOOL_EXERCISES`; the converter prints `note: N spark exercise(s) left out`. The runnable cells (`executable_spark`) are lesson content and stay. Image folders are `_images/`.
- **The "Official <Tool> resources" panel (tools/airflow, dbt, kafka):** a `<section data-tool-partner-panel="<tool>">` after Key Takeaways (logo, version, quote, doc buttons, and for Kafka a topic/link table). It is not a note block. `clean()` drops it. The trademark line after it stays.
- **The interactive pipeline-architecture exercise:** a live drag-and-drop widget; a screenshot shows an empty canvas.

## Repo facts

- `lessons/` is tracked and committed on purpose; per the user, DataDriven's people approved this copy.
- Python tooling lives in `.venv/`; Playwright's Chromium sits in `~/.cache/ms-playwright`.
- `tools/__pycache__/*.pyc` is tracked and changes on every run, so `git add` files by path.

- **Animation videos (Spark and any `*_animation` made with `--screenshots`):** `record_animations` records each mode as an MP4 into `ANIM_DIR` (default `.animations/`, git-ignored; never commit it) with Playwright's built-in video recorder, not per-frame screenshots (those stalled the page: slow motion, about 4 frames a second). It first measures the player in a throwaway 1150x1600 window, then records in a window whose height is the player height plus 40 px (a shorter window cuts the player off and the crop lands on the wrong region). The window and the recording are 2x pixels with page zoom 2, so small table text stays sharp; the crop is the player box, trimmed from the moment it is in view to the last step plus 2 s, and encoded at 1600 px wide, 30 fps. Each file is checked (duration near the live playback time, at least 10 distinct frames a second) and re-recorded if it fails; record one at a time, never in parallel (parallel browsers slow the page itself). A player with no step counter ends when its markup has been still for 4 s. `upload_animation` posts the file to GitHub's user-attachments endpoint (needs `gh auth login`; the token goes through a mode-600 temp curl config, never on the command line) and the Markdown gets the bare URL on its own line, which GitHub renders as a video player. `tools/animation_urls.json` maps recording name to URL, so a re-run reuses uploads; delete a key to force a re-upload after re-recording. The player's camera pans on purpose, so a card cut at an edge in one frame is normal; the player is at most 1102 px wide.
